## 1. 背景：为什么要改

实测（40×40 网格 = 1600 顶点 / 3120 约束 / dim 4800；300 子步；迭代上限 40；残差门槛 0.3·|g|；
**两侧迭代数 40.00、末次残差 8.63991 m/s²、最终应变完全相同**，只有线程数不同）：

| | 1 线程 | 18 线程 | 比 |
|---|---|---|---|
| 单子步 | **6.121 ms** | **12.321 ms** | 慢 **2.01×** |
| 总耗时（300 子步） | 1.836 s | 3.696 s | 慢 2.01× |

即：**当前的多线程是净减速**，而且这个负收益还污染了所有性能基线（同工况重复运行时，
单线程的全局回代稳定在 ±3%，而局部步与散射的耗时波动 1.5–2.1×）。
`docs/plan.md` M2 的验收项"8 线程相对单线程在局部步上加速 ≥5×"**目前未达成**（局部步 18 线程仅与串行持平）。

### 1.1 收益的物理上界（必须写在前面）

同一工况下**全局回代占 68%（1 线程）/ 46.5%（18 线程）**，而它是 Eigen `SimplicialLDLT`
的单线程前代+回代。因此：

> 本方案的目标是**把 2× 的倒退收回来、并让并行第一次真正略有收益**，
> **不是**让帧率翻倍。帧率的大头只能来自减少迭代/减少全局步（收敛侧）或并行求解器（M5/M6）。
> 引用本方案的收益时必须同时给出机时与工况，否则数字会被误读（见 `README.md` §3.5 的三次对照表）。

## 2. 当前流程（改造前）

### 2.1 一个子步的完整流程

```
stepOnce（每个子步调用一次）                                       并行？      实测（18 线程 / 12,000 次迭代）
────────────────────────────────────────────────────────────────────────────────────────────────
1. ensureBuffers                             尺寸检查（幂等）       串行        —
2. positionsBeforeStep = positions           拷贝 O(N)             串行        —
3. 预测 x̂ = x + h·v + h²·g                    O(N)                  ❌ 串行      0.85 ms / 300 子步
4. computeStamp +（条件）组装 L + 分解        仅 stamp 变化时        ❌ 串行      1 次，~3.5 ms（一次性）
5. 惯性右端 bBase = (M/h²)·x̂                  O(3N)                 ❌ 串行      未计时（落在"其它"）
6. for k in 1..K（K = 迭代上限）：
   6a. project（局部步）→ targets[edge]   ┌─ #pragma omp parallel ─┐  ✅ 并行     31.8 µs/次（含有效工作 7.7 µs）
   6b. b = bBase（拷贝）                    │  每调用一次就          │  ❌ 串行     —
   6c. scatterInto（散射）                  │  fork/join 一次        │  ✅ 并行     77.9 µs/次（含归约流量 69 µs）
   6d. applyPinRhs（覆盖 pin 行）        └────────────────────────┘  ❌ 串行     —
   6e. solver->solve（前代+回代）                                  ❌ 串行     143.2 µs/次 ← 占比最大
   6f. unpackPositions                                             ❌ 串行     —
   6g. 收敛判据：diff/scale 扫描 O(N)                               ❌ 串行     —
       nonlinearResidual O(E+N)（每迭代重算全场投影）                ❌ 串行     34 µs/次（**无计时包裹**）
   6h. previous = positions（拷贝 O(N)）                            ❌ 串行     —
7. 速度更新 + 阻尼 + pin 清零                  O(N)                 ❌ 串行      2.6 ms / 300 子步
────────────────────────────────────────────────────────────────────────────────────────────────
每子步的并行区域开关次数 = 2 × K（K=40 → **80 次/子步、24,000 次/300 子步**）
```

### 2.2 并行点只有两处，且都靠"私有缓冲 + 归约"

| | 局部步 `project` | 散射 `scatterInto` |
|---|---|---|
| 并行手段 | `parallelFor(edges)`、`schedule(dynamic,64)` | 每线程一份**全维**缓冲 + 结束后按线程号升序归约 |
| 回退分支 | `edges < 256` 或单线程 → 串行 | 同左（并另有 `#ifdef _OPENMP` 无 OpenMP 分支） |
| 冲突源 | 无（写 `targets[c]`，逐边独立） | **同一顶点被多条边累加** |
| 设计依据 | `docs/plan.md` D7：不用浮点原子加，保证"结果与线程数无关"且能映射到 GPU | 同左 |

### 2.3 三个开销来源（已定量，互相独立）

| # | 来源 | 量级 | 证据 |
|---|---|---|---|
| ① | **每次调用的区域开关**（fork/join：唤醒 + barrier + 汇合） | **10–25 µs/次**（18 线程）；**建池一次性仅 1–4 ms**；只配置线程从不进区域 ≈ 0 | E1 截距外推、E2（10×10 网格走串行回退：1T 0.487 s vs 18T 0.520 s）；局部步超额不随工作量增长：40×40 **+24.1 µs**、100×100 **+5.2 µs**、200×200 **+14.0 µs** |
| ② | **散射归约的内存流量 O(P·dim)** | 40×40 **1.38 MB/次**（模型 69 µs vs 实测超额 72.5 µs）；100×100 8.64 MB（430 vs 429）；200×200 34.6 MB（2880 vs 2848） | 三个规模误差 <3%；搬运/有效 ≈ **P/2 ≈ 9×**（4-邻域网格上 $2P\cdot\text{dim}/6E = P/2$） |
| ③ | **线程池活跃期间串行段被拖慢** | 回代 **1.38×**（18T）/ 1.12×（8T）；残差 ≈1.6×；拷贝 ≈1.4× | 与线程数单调；E2 证明不是"配置"引起，疑与 SMT 兄弟核被自旋线程占用有关（**未定论**） |

补充：③ 之下还有一笔**没被计时**的钱 —— `nonlinearResidual` 每迭代重算全场投影，串行，
1 线程 0.021 ms/迭代、18 线程 0.034 ms/迭代，累计 **250–410 ms / 12,000 次迭代**，全部落在"其它"桶（19.2%）。

### 2.4 确定性的现状（改造前）

`parallelScatterMatchesSerialReference` 实测：并行分支与串行分支**位级不同**（最大差
7.11e-15，≈ 典型分量的 1 ulp），16 次跨线程/重复运行里只有 2–3 次位级相同（两次运行分别给 2 和 3）。
即"与线程数无关"目前只是 **1e-12 量级内**的性质（满足 `docs/plan.md` M2 判据），
**不是位级性质** —— `schedule(dynamic,64)` 的分块分配会变，求和分组随之变。

## 3. 修改后的流程（目标形态）

```
stepOnce（每个子步调用一次）
──────────────────────────────────────────────────────────────────────────────────────────
1-2. 尺寸检查 / 保存上一步位置（逐顶点可融合，串行或并入区域第一趟）
3. #pragma omp parallel                       ← 一个子步只进/出一次（全子步唯一一次 fork/join）
   {
     omp for nowait : 预测 x̂ = x + h·v + h²·g
                      融合：同一趟里立刻写 bBase = (M/h²)·x̂         （一次遍历，不再两趟）

     for k in 1..K:                                                  （迭代循环留在区域内）
       for c in 0..C-1:                                              （C = 约束颜色数；同色内无冲突）
         omp for    : 融合的"投影 + 散射"：就地算 d_c 并直接累加到两端点
                      （c=0 时以 bBase 为基数写，其余颜色累加 → 省掉整次 b = bBase 拷贝）
       omp for nowait: 覆盖 pinned 行（写集合与散射不交）
       omp single   : solver->solve（Eigen 单线程；区域内只有 1 个线程干活，其余等在 barrier）
       omp for nowait: 解包 + 收敛扫描（局部 max）
       [需要时] omp for: 非线性残差（同色复用同一套颜色；逐顶点累加）
       omp barrier  : 迭代末尾汇总
     omp for nowait : 速度更新 + pin 清零
   }
──────────────────────────────────────────────────────────────────────────────────────────
每子步的并行区域开关 = 1 次；barrier ≈ (C + 2) × K 次
```

### 3.1 前后对比（一表看清）

| 维度 | 改造前 | 改造后 |
|---|---|---|
| 并行区域开关 | **2 × K / 子步**（40 迭代 → 80 次） | **1 次 / 子步** |
| 同步形式 | fork/join（10–25 µs/次） | 区域内 barrier（1–5 µs/次） |
| 散射的顶点累加 | 每线程一份全维缓冲 → 归约 `P × dim`（≈9× 浪费） | 同色边互不相邻 → **直接写，无归约** |
| 求和顺序 | 动态分块的任意分组 → 按线程号归约（位级不可复现） | **颜色序固定**（顶点每个颜色只被写一次） |
| 预测 / 惯性右端 / 速度更新 | 各自独立、全串行 | 区域内的逐顶点循环，且**互相融合**（少遍历、少 barrier） |
| `targets` 中间量 | 写 75 KB + 读 75 KB / 迭代 | 与散射融合后**不再物化**（保留函数接口供测试调用） |
| `b = bBase` 拷贝 | 每迭代一次 O(3N) | 由颜色 0 轮以"赋值"取代（省一次拷贝） |
| 非线性残差 | 全串行、无计时 | 并行 + 与收敛扫描融合 |
| 全局回代 | 串行（46–68%） | **不变**（本轮不动；这是 Amdahl 上界） |
| 数学语义 | — | **不变**：投影/散射/矩阵块/pin 消融补偿全部不变，只改"谁在什么顺序里算什么" |

## 4. 三个改造点

### 4.1 一个子步一个区域（fork/join → barrier）

**现在为什么贵**：`#pragma omp parallel` 写在 `project` 与 `scatterInto` **函数内部**，
函数一返回线程就解散。所以每调用一次 = "集合所有线程 → 干一段活 → 解散"一次。
每子步调用 `2 × K` 次（40 迭代 → 80 次），而每次集合/解散就要 **10–25 µs**，
比局部步的有效工作（7.7 µs）还长。

**改后**：把 `#pragma omp parallel` 提到 `stepOnce` 最外层 —— **开门一次，整子步都在里面**。
原来各函数里的 `parallel` 换成 `#pragma omp for`（区域内的分工），
不需要立刻同步的地方加 `nowait`；真正需要同步的地方保留 barrier（约 1–5 µs）。

**通俗版**（写进注释也用这个说法）：
> 想象 17 个工人 + 1 个工头。**现在**的做法是：每做一件 8 微秒的小活，工头都要跑到门口
> 把 17 个人全叫进来，干完再让他们全出去 —— 一天要叫 80 次（每子步），
> 光"集合/解散"就比干活本身贵 3 倍。
> **改后**的做法是：早上开门叫进来一次，整天都在车间里；换工序时只需喊一声"都干完了吗"（barrier），
> 不用重新集合、重新解散。

**为什么当初不是这么写的**：`project` / `scatterInto` 是独立可用的库函数，各自管自己的并行是
"库式"写法的自然结果；把它提到调用方（`stepOnce`）需要对整条链路的依赖关系做一次统一梳理（见 §6.2）。

### 4.2 逐顶点融合（多次遍历 → 一次遍历）

**"逐顶点阶段"**= 那些只读自己、写自己的循环：预测、惯性右端、解包、收敛扫描、逐顶点残差、速度更新。
它们**没有跨顶点写冲突、不需要归约** —— 这正是"以顶点为单位并行"天然合法的原因，
也是它们**不需要图着色**的原因（需要着色的是"约束"级别的散射与残差累加）。

**"融合"**= 把多次遍历同一批数组的循环合并成一趟：

```cpp
// 融合前：3 趟，每趟都要重新读一遍 positions / velocities / predicted
for (v) predicted[v] = pos[v] + h*vel[v] + h*h*g;
for (v) { bBase[3v+0] = mOverH2 * predicted[v].x; ... }
for (v) maxdiff = max(maxdiff, maxAbsComponent(pos[v] - previous[v]));

// 融合后：1 趟，刚算出来的 x̂ 还在寄存器/L1 里就被用掉
for (v) {
  const Vec3 xh = pos[v] + h*vel[v] + h*h*g;
  predicted[v] = xh;                         // 仍需物化：迭代循环要读它
  bBase[3v+0] = mOverH2 * xh.x; ...          // 立刻用掉，不再单独读一遍 predicted
  maxdiff = max(maxdiff, maxAbsComponent(pos[v] - previous[v]));
}
```

收益两层：① 省内存往返（每子步几微秒量级）；② **少一个 barrier** —— 在"一个区域"方案里
barrier 数是主要残存开销，所以这一条比看起来重要。

**最强的一处融合（需要着色配合）**：把 `project` 与 `scatter` 合成一趟 —— 每个颜色轮里，
边 e 用当前位置直接算 $d_c$ 并**立刻**加到两端点，`targets` 那块内存（写 75 KB + 读 75 KB / 迭代）
整个消失。前提正是"同色边互不相邻"。

### 4.3 图着色：用通用并行算法，不写死网格解

> **实施结果（2026-09-21）**：算法最终用的是 **Jones–Plassmann**（优先级 + "取最小可用颜色"），
> 不是纯极大独立集迭代 —— 后者实测给 40×40 用了 **15 色**，而每次散射的颜色轮数 = 颜色数、
> 每色一个 barrier，等于把省下的流量又吃回去；换成 JP 后是 **6 色**。
> 另外必须让**同色内按顶点序排列 + 静态连续分块**，否则假共享会吃掉全部收益
> （实测散射反而慢 1.87×）—— 详见 `docs/perf.md` §3.1/§3.3。

**目标**：让散射（以及同构的残差累加）不再需要"私有缓冲 + 归约"。

**关键约定：着色对象是"约束"（边），不是网格顶点。**
散射的冲突是"两条约束共享一个顶点"，所以冲突图的**节点是约束**，两个节点相邻当且仅当共享顶点
（即网格图的**线图**）。在线图上做恰当着色 = **边着色**：同色约束两两不相邻 ⇒ 并发写 `b` 无冲突。
> 若改在**网格顶点**上做顶点着色，配的就不是 scatter 写法而是 **gather 写法**（每个顶点自己读自己的
> 关联边、只写自己的 `b[v]`）—— 那种写法连颜色都不需要，只需要一个分区。两条路线见 §8 待拍板项。

**算法**：并行着色迭代 ——
① 给每个节点一个权重；② 本轮里"所有邻居都已着色"或"权重比所有未着色邻居都大"的节点，
取**最小可用颜色**（避开已着色邻居用掉的颜色）；③ 未着色的节点进入下一轮，直到全部着色。
这是 Jones–Plassmann 的做法，颜色数上界 **Δ+1**，且**对不规则网格同样适用**
（这正是选它而不是网格闭式 4 色的原因）。

**必须遵守的三条工程约定**：

| 约定 | 原因 |
|---|---|
| 权重必须是**确定性哈希**（索引的整数哈希，固定常数/种子），不能用 `rand()` | 否则每次运行颜色不同 → 求和顺序不同 → 结果不可复现，直接违背 `docs/plan.md` M2 的验收前提 |
| 颜色是**拓扑级信息**：算一次、缓存、随 `topologyId` 失效（与 `Mesh::blockPattern()` 同生命周期） | 着色是 $O(E)$ 的一次性成本，不该进每帧预算 |
| 颜色数 $C$ 直接决定每次散射的 barrier 轮数 | 网格线图最大度 6（理论最少 4 色）。实测 JP 给 40×40 **6 色**（记入 `docs/perf.md` §3.1）；纯 MIS 迭代会给 15 色，**不可用** |

**它能换来的最硬收益**：位级确定性变成**结构性保证** —— 顶点在每个颜色只被唯一一条边写一次，
累加顺序固定为颜色序 0,1,…,C−1，**与线程数、分块、调度完全无关**。§7 Phase 2 会把
Phase 0 新增的跨线程测试从"≤1e-12"收紧为"位级相同"。

#### 4.3.1 它是多次迭代的方法 —— 分清两个"轮次"

**是多次迭代的**，但要区分两个不同时间尺度，否则会把成本算错：

| | 算法内部的迭代轮次 | 每次散射的颜色轮次 |
|---|---|---|
| 是什么 | 每轮取"权重比所有未着色邻居都大"的节点，作为**一个**独立集 → 分配一种颜色 → 从未着色集合里移除 → 下一轮 | 散射按颜色分组执行：第 0 色所有边先算，再第 1 色… |
| 轮数 | **等于颜色数 $C$**（每轮恰好产出一种颜色）。随机权重下期望 $O(\log n)$；本方案用**确定性哈希权重**，所以 $C$ 对给定网格是**固定值**（同网格任何时刻、任何线程数都得到同一套颜色） | 也是 $C$ 次，但每次都在**帧内热路径**上 |
| 什么时候发生 | **一次**：场景构建/拓扑变更时（拓扑级、随 `topologyId` 失效，与 `blockMesh` 的稀疏结构同生命周期） | **每子步 $K$ 次迭代各一次**（$K$ = 迭代数） |
| 成本 | $O(\text{轮数} \times E)$ 一次性，进不了帧预算 | $C$ 个 barrier/**每次散射**，这是 §5 里"新增 barrier ≈0.1–0.2 s"的来源 |
| 是否要缓存 | 要：颜色 + 按颜色分组的边表（连续存放，便于顺序访问） | 不涉及 |

一句话：**算法是迭代的（多次），但只在拓扑变化时跑一次；热路径上付的是"按 $C$ 种颜色分组执行"的 $C$ 个 barrier。**

## 5. 预期收益（40×40 / 40 迭代 / 300 子步，18 线程；总 3.696 s，对照 1 线程 1.836 s）

| 阶段 | 回收项 | 预期单子步 | 预期总耗时 | 相对 1 线程 |
|---|---|---|---|---|
| 现状（改造前） | — | 13.87 ms | 4.160 s | 慢 2.20× |
| ＋Phase 1（一区域 + 逐顶点融合） | 区域开关 ≈0.39 s，新增 barrier ≈0.1–0.2 s | ≈11.0–11.4 ms | ≈3.3–3.4 s | 慢 1.8× |
| ＋Phase 2（边着色替代归约） | 散射流量 ≈0.83 s | ≈7.0–7.5 ms | ≈2.4–2.6 s | 慢 1.3–1.4× |
| ＋Phase 3（残差并行/融合） | ≈0.2–0.4 s | ≈6.8–7.2 ms | ≈2.1–2.3 s | **接近持平** |
| （不在本轮）Phase 4：串行段与线程池共存 | 回代/拷贝被拖慢的 1.13–1.38× | — | — | 才有可能真正领先 |

## 6. 风险与必须守的不变量

### 6.1 语义不变量（不得改变）

1. 投影方向只由端点顺序决定 $d_c=\ell\cdot\mathrm{unit}(x_a-x_b)$，**无 pin 特例**；
2. 散射符号 `b_a += κ d_c`、`b_b -= κ d_c` 与 **pin 消元补偿** $b_{\text{free}}\mathrel{+}=\kappa q$；
3. 矩阵块 $+κI / -κI$、pinned 行精确为 $(\text{对角}=1,\ b=q)$、**只跳过两端都 pin 的约束**；
4. `L` 与位形无关 → 分解复用（`SolverStamp` 语义不变，本轮**不引入新的重分解触发条件**）；
5. `pinPositions` 契约（有 pinned 就必须填满）与现有快速失败检查；
6. `project` / `scatterInto` **保持为可独立调用的公开函数**（`tests/`、`_verify/direction_audit`、
   `PD_TRACE_STEP` 诊断都直接依赖它们）；融合只能作为**快路径**增加，不能删接口。

### 6.2 `nowait` 的依赖边界（逐处都要有论证）

| 边界 | 能否不设 barrier | 理由 |
|---|---|---|
| 预测 → 写 bBase | ✅ 可在同一趟里做 | 同顶点同线程，无跨线程依赖 |
| 局部步/投影 → 散射 | ❌ 必须 | 散射读的是边的投影结果（融合方案下二者同一趟，内部无依赖） |
| 散射 → 覆盖 pin 行 | ✅ `nowait` | 散射跳过 pinned 顶点，写集合不交 |
| 散射 → 全局回代 | ❌ 必须 | 回代需要完整的 `b` |
| 回代 → 解包/收敛扫描 | ❌ 必须 | 解包读 `xSolution` |
| 迭代末尾 | ❌ 必须 | 收敛判据需要全局 max |
| 各颜色轮之间 | ❌ 必须 | 同一顶点的累加必须按颜色序（这正是确定性的来源） |

### 6.3 工程纪律（`docs/contributing.md`）

- **先写断言再改实现**（§2）：Phase 0 已补并行分支对照与跨线程一致断言；Phase 2 需再补
  "同色边不共享顶点""颜色数 ≤ Δ+1""颜色确定性（同网格两次着色逐位相同）"三条结构断言。
- **禁止静默降级**（§3）：本方案**不引入运行时双实现开关**。旧实现作为历史保留在 git 里，
  正确性锚点是测试里的独立参考实现；A/B 对照用分支或 `git stash` 做，不做永久开关。
- **热路径改动要更新性能记录**（§6）：本轮应**创建 `docs/perf.md`**（至今仍缺），
  按"预热后统计、分阶段耗时与占比、线程数 1/2/4/8/16、不假设线性加速"的口径记录改造前后。
- 文档同步：`README.md` §3.5 的性能数字、§5 第 7 项状态；`docs/code-map.md` §2.4/§2.5 的描述。

## 8. 已拍板（2026-09-21）

1. **冲突图粒度：边着色 + scatter 写法**（不做顶点分区 + gather）。
   即：冲突图的节点是**约束**，两节点相邻当且仅当共享顶点；在线图上做恰当着色。
   理由：与 GPU 路线（M5）的无原子/合并写一致，且不需要引入邻接表与"每条边被访问两次"的算术。
2. **颜色轮次预算：接受**。即接受"颜色数 $C$ 可能大于网格理论最少的 4"（线图最大度 6），
   用"多几个 barrier"换"位级确定性 + 消除归约流量"。实测 $C$ 要记入 `docs/perf.md`；
   **不在测试里断言 $C$ 的上界**（MIS 迭代法的颜色数上界缺少可援引的证明，写下来就是假门槛），
   只断言"恰当性"（同色边不共享顶点）并**记录**实测值。
3. **线程数策略：暂不动**（不做"按规模选线程数"的止血措施）。先把三个结构性原因修掉，
   再看是否还需要止血；若要动，属 Phase 4 的决策范围。
5. **默认线程数：已定为 4（机器相关参数，需重标定）**。理由与标定表见 `docs/perf.md` §6。
   运行时仍可用 `setNumThreads()`（bench 的 `--threads`、查看器的 `;` `'`）覆盖。
   换机器或换到 ≫10 万约束的量级时，这个值必须重新测 —— 与刚度 κ 的处理方式一致。

4. **`docs/perf.md`：本轮创建**。在 Phase 1 开工时建立，按 `docs/contributing.md` §6 的口径
   记录改造前后（固定工况、预热后统计、分阶段耗时与占比、线程数 1/2/4/8/16、不假设线性加速），
   本方案的收益数字全部落在它里面，README 只保留指针。
