## 1. 优化机会（按预估收益排序）

### 1.1 迭代预算：**保持可调**（不做硬性规定）

- **是什么**：`SceneConfig::maxIterations` / `pd_bench --iters`。瞬态实际到不了判据，
  所以它就是一个**可调参数**，按用途取档即可 —— 不必（也不应该）锁死一个值。
- **为什么有效**：时间与迭代数**几乎严格成正比**（每迭代 = 一次"局部步→散射→回代→解包+判据"），
  而回代占 57 % ⇒ 少一半迭代就是近乎线性的一半时间。
- **量级与依据**：实测（40×40/300 子步）40 → 20 迭代 = **−49 %**，最终弹性能只差 **0.5 %**；
  瞬态残差 400 次迭代后仍停在 5.7 m/s²（判据 = 0.3·|g| = 2.943），每次只降 ~0.3 % ⇒
  **瞬态的迭代数是硬截断**，不是"算到收敛"。
- **是否改变数值**：⚠️ 是（能量差 0.5 %、末次残差显著变化）⇒ 按用途分档，例如：
  交互预览可以取小（20 甚至更少，换帧率）；离线对照 / 回归基线取大（40–80，换精度）。
  分档时要连同"末次残差"一起记录，别只写迭代数。
- **怎么验**：`pd_bench --iters 10|20|40|80` 四档对照（命令见 `solver-feasibility.md` §8），
  看应变 / 能量 / 收敛统计三组物理量。
- **备注**：若要求"同样精度但更快"，则要换方法（Chebyshev 外推 / APD / 多重网格），
  那是一次**方法改造**，要重新验收全部物理正确性（`docs/pd-convergence.md` §5.2 有候选清单）。

### 1.2 ✅ 投影与散射融合（已完成 2026-09-22：**−13.8 %**，**逐位不变**）

- **做了什么**：每迭代原来是两趟（`projectInRegion` 物化 `targets` → `scatterIntoInRegion` 读它累加），
  现在合成一趟按颜色就地算 `d_c` 直接累加，`targets` 不再物化。
  **两条路共用同一份算术 helper** ⇒ 每个操作与操作数顺序逐字相同 ⇒ **结果逐位相同**（已用三档工况逐字比对）。
- **量级（同轮交替 5 次取最小）**：40×40/iters40/4T **3.081 → 2.656 ms/子步 = −13.8 %**
  （"局部步+散射"桶 193 → 90.9 ms，−53 %）；18T −12.0 %；交互档 −8.0 %；100×100 −8.5 %；200×200 −3.1 %。
  远大于原先"粗估 3–8 %"——大头是 `targets` 的写+读（40×40 是 75 KB，装不进 L1）与位置数组的重复读取。
- **副作用（口径）**：`局部步` 与 `散射` 两个桶合并成 `投影+散射`（bench 显示与看板图例都已改）；
  引用历史占比时要相加再比。
- **回归断言**：✅ 已补 `fusedProjectScatterMatchesSplitPath`（在并行区域里调融合函数，与两趟路径
  `memcmp` 逐位比较）—— `test_primitives` 130 → **132** 断言，三套合计 **302**。

### 1.3 因子只存一份（未测，主要对大规模有意义）

- **是什么**：`L = Ã ⊗ I₃` ⇒ 因子的三个分量块**结构同构、数值完全相同**（实测每分量 nnz 相等：
  40×40 各 22,009；100×100 各 212,411；200×200 各 1,085,011）。现在它们在同一个 CSC 因子矩阵里
  **各存了一份**。理论上可以只存一份标量因子 + 分量映射，三条线程用同一份因子配不同右端。
- **为什么有效**：内存足迹降到 1/3（200×200：39 MB → **13 MB**，按每非零 12 B 估）。
  这台的 P-core L2 是 1.25 MB、L3 是 25 MB：
  · 40×40 的因子 0.79 MB 本来就住得进 L2 ⇒ 收益很小；
  · 200×200 的 39 MB 远大于 L3，缩小到 13 MB 也仍大于 L3 ⇒ **收益不确定**，得实测。
  另外三条线程读同一份数据时，L3 里是同一份副本（现在读的是三块不同地址）⇒ 对 L3 命中率有利。
- **是否改变数值**：✅ 不改变（同一份数据、同样的列顺序）。
- **怎么验**：可以在 `pd_solvecomp` 里先量"三分量并行读同一份因子"vs"读各自那份"的单次 solve 时间，
  再决定动不动生产代码。

### 1.4 减少同步点密度（收益在散射桶里，但要**重做位级基线**）

- **是什么**：散射每迭代有 `1 + C` 个 barrier（种子趟 + C 个颜色轮，40×40 实测 C = 6）。
  减少颜色数、或把种子趟并进第一色（见 1.2），都能减少同步点数量。
- **为什么有效**：`B(P)`（每次同步的成本）在负载中实测约 **1.1 µs × 线程数**
  （4T 4.02 µs / 8T 7.32 / 18T 19.78，空载只有 0.08 µs×P —— 空载会低估 12 倍），
  且每次同步都要"等最慢者 + 18 份缓存副本失效"。同步点从 10 个/迭代降到 8 个就是 20 % 的同步开销。
- **量级与依据**：`docs/perf.md` §5 的归因表里，"散射的颜色轮 barrier + 残余写争抢"在 18T 上
  贡献了 +509 ms（占 18T−1T 差额的 46 %）。4T 下这一项小得多，预计**几个百分点**。
- **是否改变数值**：⚠️ **是**。颜色数是"顶点上各条边的求和顺序"的来源，改它会让**位级结果变化**
  （仍然是确定性的、仍与线程数无关，但不再与旧基线逐字相同）⇒ 必须重新记录物理基线，
  失去"逐位不变"这张免验收通行证。这是它比 1.2 贵得多的地方。
- **怎么验**：改 `ConstraintColoring` 的着色策略（例如合并层/贪心更少色），
  用 `test_primitives` 的着色断言 + 全部物理基线重采。
- **同族的一条已经量过（否）**：§3 表里的"惯性右端并行化" —— 把区域里另一个 `omp single`
  阶段（惯性右端）改成 `omp for`，实测**无收益**（去掉代码布局地板后 4T/18T 只剩 −1.2 %/−0.6 %，
  理论上限也只有 0.1 % 量级）：**"少一个单线程阶段"本身没有价值，得先有一个够贵的单线程阶段。**
  结论与三方 A/B 见 `docs/perf.md` §14。

### 1.5 分块流水：把回代从 3 路推到 4 路以上（改变数值，性价比低）

- **是什么**：把每个分量的因子切成两块 `[[L11,0],[L21,L22]]`，解 x1 = L11⁻¹b1（串行）→
  用 x1 更新 b2' = b2 − L21·x1（**这一步是稀疏矩阵乘向量，可按行并行**）→ 解 x2 = L22⁻¹b2'。
- **为什么"可能"有效**：现在 4 线程里只有 3 条在干活（3 个分量），第 4 条空转；分块后更新段变成 6 路可并行。
- **为什么**性价比低：三段之间有先后依赖，只有中间那段能多拿并行度（平均 ≈3.5–4 路），
  还要再加上同步；而**求和顺序会变**（更新项与块内的项不再按"对方列号递增"逐个相减）
  ⇒ 不再逐位不变 ⇒ 要重做物理基线。收益小 + 代价大 ⇒ 排在最后。

### 1.6 换全局步形态（量级大，但都是大工程）

- **1.6.1 迭代法替代直接解**（Chebyshev 半迭代 / CG / 多重网格 / 近似逆）：把"延迟受限的串行链"
  换成"带宽受限的 SpMV 序列"，天然高并行。代价：全局步变成**不精确求解**，外层 PD 迭代数与收敛
  行为会变（要重新验收）；而且门槛被 Phase 4c 抬高了 —— 直接法已经快了 2.0–2.8×。
- **1.6.2 超节点 + 嵌套剖分(ND) + 依赖计数 + 工作窃取**（CHOLMOD/SuperLU_DIST 形态）：
  真正的可扩展并行三角求解形态（同步次数 O(深度) 而不是 O(层数)）。需要：换排序（现在 AMD 的关键路径
  310/1042/2250 层）、稠密块核、自建线程池（MSVC 经典 OpenMP 连 `task` 都没有），且自建同步在 18T 上
  实测会**活锁**（必须带 yield 回退）。
- **1.6.3 GPU Chebyshev（M6）**：唯一能从根上"消除"串行段的路线（见 `docs/plan.md` M6 与 D13）。
- **是否改变数值**：⚠️ 三者全部要重新验收物理正确性。

### 1.7 ✅ 数字收尾（已完成 2026-09-22）

- **200×200 长日志**：原先 A/B 与看板里 200×200 只用 8–12 子步，一次性"组装+分解"被摊进
  单子步 ⇒ 报出的 −28.6 % 偏保守。**补跑 100 子步后（同轮交替 3 次取最小）：旧 107.64 ms →
  新 59.54 ms = −44.7 %**，与 100×100 的 −49 % 同量级 —— 说明大规模上的收益比原先报的更好。
- **查看器重测**（`pd_viewer --frames 400`，60×60）：稳态 **60 FPS、物理 0.55–0.59 ms/帧、
  迭代 1 次、残差 2.90**（Phase 4c 之前是 0.90 ms/帧 ⇒ **−39 %**，与 bench 的 60×60/iters2
  −41.9 % 一致）；瞬态 **11.9–13.1 ms/帧**（原先 23–27 ms/帧）。
- **4 线程仍是最优**：复测 4T vs 5T（40×40/iters40，交替 6 轮取最小）4T 3.015 / 5T 3.052
  ⇒ **+1.2 %**，之前看到的"5T 好 2.3 %"是噪声，**默认值不动**。

### 1.9 🆕 **填充量不是约束数的单调函数**：给含弯曲的矩阵找一个更好的排序（观察，未做实验）

- **是什么**：2026-09-23 采"四套约束集的阶段构成"（看板 §十）时偶然发现 —— 同一工况下，
  **「剪切 + 弯曲」的 `L` 非零比"只加弯曲"更多，但因子 nnz 反而更少**：

  | 工况（4 线程） | 只加弯曲：L nnz → 因子 nnz | 两者都开：L nnz → 因子 nnz | 结果 |
  |---|---|---|---|
  | 40×40 / iters40 | 41,712 → 182,613 | 50,832 → **170,247** | L +21.9 %，因子 **−6.8 %** |
  | 60×60 / iters2 | 94,992 → 564,858 | 115,872 → **530,598** | L +22.0 %，因子 **−6.1 %** |
  | 100×100 / iters10 | 266,352 → 2,132,901 | 325,152 → **1,933,950** | L +22.1 %，因子 **−9.3 %** |

  于是 100×100 上"两者都开"比"只加弯曲"**还快**（19.9 vs 26.0 ms/子步）。
  **这是确定性指标（因子 nnz 与时间无关），不是时间噪声**；三档方向一致。
- **为什么**：填充量由"消元顺序 + 整体结构"共同决定。加剪切对角边改变了图，AMD 给出的排序随之改变，
  而**新排序对弯曲那部分结构恰好更省填充** —— 也就是说，我们**从没为"含弯曲的矩阵"专门挑过排序**。
- **为什么值得做**：`docs/solver-feasibility.md` 里"换排序"那一节是在**默认约束集**上试的
  （当时结论是 AMD 已经不错）；弯曲把矩阵结构整个改了，那条结论不能照搬。
  若能在"只加弯曲"的矩阵上找回同样 6–9 % 的填充，等于把弯曲的代价从 +75 % 压到 +60 % 量级。
- **怎么做（建议的最小实验）**：`pd_solveaudit --order amd|nd|natural` 现成可用；再加一档
  不同参数的 AMD / ND。**先量"因子 nnz"（确定性、秒级）再量时间** —— 找到更好的排序才值得量时间。
- **风险**：换排序会改变**求和顺序** ⇒ 不再与旧物理基线逐位相同（与 §1.4 同一个代价）；
  但"因子 nnz 下降"这一步可以完全不碰数值就预筛出来。

## 2. 现存问题（按严重度排序）

### 2.1 ⚠️⚠️ **IPC 会破坏 `⊗ I₃` 结构（战略问题）** —— **优先级已下调（2026-09-22 决定"先放着"）**

> **2026-09-22 状态**：项目**当前不一定会接 IPC**，所以这条先不做处理（不加告警、不加门禁）。
> 但它仍然写在这里，因为一旦决定接 IPC，**必须先处理这条**，否则会以"某天突然慢一倍但没人知道"
> 的形式出现。只要能量项集合还是"距离约束 + 各向同性质量 + pin"，这 2–3× 就一直在
> （`pd_solvecomp` 的第一节可以随时自检：跨分量填充必须为 0）。
>
> 下面保留原始分析。

- **是什么**：Phase 4c 的全部收益建立在 `L` 的每一块都是**标量 × I₃** 之上。
  项目最终目标包含 **IPC**（增量势接触），而 IPC 的 barrier / friction Hessian 是
  **一般的（非各向同性）3×3 块**。
- **为什么会出问题**：非各向同性的块会让消元填充**跨越"分量"**（现在三个分量是三个互不相连的连通分量），
  `EigenDirectSolver::buildComponents()` 的检查会命不中 ⇒ `parallelComponents()` 返回 1 ⇒
  **功能仍然正确，但那 2.0–2.8× 的加速静默消失**，回到 Phase 4b 的水平（多出 ~40 % 时间）。
- **量级与依据**：`pd_solvecomp` 的第一节会直接打印"跨分量的 i≠j 项"，现在三档规模都是 **0**；
  引入接触项后这个数会 > 0。
- **怎么修/怎么办**（三选一，需要拍板）：
  ① **接受**：CPU 直接法路线在接触场景下退回 Phase 4b 的速度；
  ② **为接触项设计保持结构的形式**（例如接触力只用对角近似、或把接触块放在单独的子系统里）；
  ③ **不再指望这条**：把大网格的并行寄望于 1.6.2 / 1.6.3。
- **配套动作**（无论选哪条都要做）：把 `pd_solvecomp` 纳入验收集当门禁或给它加断言，
  否则这件事会以"某天突然慢了 2 倍但没人知道"的形式出现（见 2.2）。

### 2.2 结构回退是**静默**的

- **是什么**：`IGlobalSolver::parallelComponents()` 在结构不满足时返回 1，`Integrator` 就退回整趟求解。
  这个设计是**故意的**（保证新矩阵形态不会算错，只会变慢），但它**不打印任何提示**。
- **影响**：配合 2.1，将来加速丢失时没有任何信号；性能回归会被归因成"机器变了"。
- **建议**：回退时打印一次告警（`std::fprintf(stderr, ...)` + 一个 `static bool` 只打一次），
  并在 `pd_bench` 的输出里明写"本次运行的全局步是 X 路并行"。

### 2.3 ✅ **已修**：`solveComponent` 的统计竞争（本轮改造引入，同日修掉）

- **曾经的问题**：`EigenDirectSolver::solveComponent()` 里三条线程会并发执行
  `stats_.lastSolveSeconds = ...` 与 `stats_.totalSolveSeconds += ...`（非原子读-改-写）
  ⇒ 形式上是数据竞争（C++ 层面 UB）。量级极小（每线程 12,000 次累加、单次窗口几纳秒、
  间隔约 200 µs ⇒ 整轮期望丢更新 < 1 次），但诊断数字也不该有 UB。
- **修法（已实施）**：`IGlobalSolver` 新增 `noteSolveStage(double)`；
  `Integrator` 在求解阶段的 barrier 之后**由单线程（thread 0）调用一次**，把阶段墙钟交给
  求解器记账；`solveComponent()` **完全不碰 `stats_`**（只做计算）。
  `parallelComponents() == 1` 时 `noteSolveStage()` 是无操作（那条路 `solve()` 自己已经记过，
  否则会重复计数）。
- **口径变化（要记住）**：`Stats::totalSolveSeconds` 现在是**阶段墙钟的累计**
  （与 `StageTimes::solve` 同口径），不再是"各分量工作量之和"。
  `app/bench/main.cpp` 的"单次回代"相应改成 阶段墙钟 ÷ 次数 —— 与阶段表 `全局回代 / 迭代数`
  一致，也与"回代快了 2 倍多"这件事自洽（它本来就该变小）。
- **验证**：`pd_check` 8/8、300 断言全过；与改动前二进制**物理输出逐字相同**（含
  `回代 4800 次` 这个计数）。

### 2.4 "全局回代"桶的口径变了，历史数字不可直接比较

- **是什么**：Phase 4c 之前该桶是 `omp single` 里"唯一执行者自己的执行时间"（**不含** barrier 等待）；
  现在是按分量 `omp for` 之后的**阶段墙钟**（**含**等最慢的那条线程）。
- **影响**：引用历史上"回代占 76 %"之类的数字时会得出错误结论。
- **现状**：已在 `docs/perf.md` §9.6、`build/_perf/HANDOFF.md` 坑 12、看板第六章注明。
  引用时必须写明口径。

### 2.5 `solveComponent` 的不 resize 契约

- **是什么**：拆分路径**刻意不 resize** 输出向量 x（多线程并发 resize 是竞争），
  要求调用方在进并行区域之前把 `xSolution` 备成长度 n，否则 `abort`。
- **影响**：将来若有别的调用方（GPU 后端、批处理、新的诊断工具）不知道这条契约，会直接崩。
- **现状**：已在 `IGlobalSolver.h` 的契约里写明；`Integrator` 靠 `ensureBuffers()` 保证。

### 2.6 M2 判据口径未按"带宽效率"改写（已记录建议，待落文档）

- **是什么**：`docs/plan.md` §M2 写的是"8 线程相对单线程在局部步上加速 $\ge 5\times$（$N\ge 40\text{k}$）"，
  200×200 实测只有 **2.36×**。
- **为什么达不到**：这不是实现问题 —— 局部步每次读写约 8.3 MB，1 线程已达 ~17 GB/s（单核带宽极限），
  8 线程 ~40 GB/s ≈ 该平台双通道峰值的 **78 %**，要 5× 需要 ~85 GB/s（超过平台能力）。
- **建议（已按此执行）**：把判据改成**带宽效率口径**（例如"≥70 % 平台峰值带宽"），
  并在 `plan.md` 的该条上加注说明 —— 已在 §M2 处补了 2026-09-22 的注。

### 2.7 `_verify/` 下约 20 个诊断程序前提过期

- **是什么**：排查期留下的诊断程序（`docs/code-map.md` §2.7），多数假设已经过期，
  **不是受支持的验收集**。
- **风险**：后人拿它当基准会得到错误结论。
- **建议**：清理或逐个加"过期/仅诊断"标注。

### 2.8 测量成本：跨会话数字不可比

- **是什么**：同一二进制同工况在会话内会漂移（实测 200×200 从 155 ms 一路降到 123 ms）。
- **影响**：任何改动都必须在**同一轮会话内交替 A/B、重复取最小值**；跨会话对比无效。
- **现状**：这是纪律不是缺陷（`docs/perf.md` §0/§6.2），但它是每条优化都要付的成本。
- **同族的一次真实事故（2026-09-23）**：A/B 脚本的日志解析把"单子步(ms)"抓成了
  `总耗时` 的**秒数**（差 3.33 倍），于是 `perf.md` §12.4/§13 的绝对数列一直标错单位
  （**比值/百分比不受影响**，所以"弯曲 +73 %"这类结论仍然成立）。已修脚本 + 修正文档。
  **教训**：解析日志要按**字段名**抓，不能"取第一个 x.y"；并且要有一条自检 ——
  这里可用的是"**各阶段累计 ms 之和 == 墙钟 ms**"（修完立刻就能对上）。

### 2.10 单线程阶段的并行化：不是免费的优化方向（已量过一条，否）

- **是什么**：区域里还剩两个 `omp single` 阶段（惯性右端、判据合并）。直觉上"把它们也并行化"
  似乎总能赚一点。
- **实测结论**：惯性右端并行化**无收益**（`perf.md` §14：1 线程档就"快" 1.7 % ⇒ 那是代码布局
  抖动；理论上限也只有 0.1 % 量级）。**代码已回退。**
- **可推广的判断**：这类阶段的价值不在"有几条线程在干"，而在**它本身有多贵** ——
  惯性右端是 O(n) 纯读写（3–5 µs/子步）、判据是 O(1) 合并，都远小于一次 barrier 的量级。
  真要让"区域里没有单线程阶段"变成收益，先得有一个**够贵的**单线程阶段。

### 2.9 自旋抢资源（Phase 4c 之后：默认档已测不出来，高线程数下仍在）

- **是什么**：等待仍然由 vcomp 的**自旋**实现（`OMP_WAIT_POLICY` 默认 active）—— 这是 runtime 行为，
  Phase 4c 没有改它，改的是"谁在等、等多久、几条线程在等"。
- **形态变了**：Phase 4c 之前，全局回代是 `omp single` ⇒ "1 条线程干活、P−1 条在 barrier 上自旋"，
  而这个阶段占单子步 57–76 %、4T 下自旋:工作 = **3:1**、18T 下 = **17:1**。
  现在按三分量 `omp for` ⇒ "3 条干活、P−3 条自旋"（4T = 1:3、18T = 5:1），
  且回代阶段本身短了 2.0–2.8× ⇒ **自旋窗口同比缩短**。
- **自旋 CPU 的绝对量**（40×40 / iters40 / 300 子步，按回代桶折算的"空转 CPU 时间"）：
  4T 从 ~280 µs/迭代降到 **~42 µs/迭代（6.7×）**；18T 从 ~2108 µs 降到 **~805 µs（2.6×）**。
- **剩余量级**（`pd_solvecomp` 两轮独立测量，单次 solve 的最小值；A 档是单线程阶段、B 档是三分量并行）：

| 线程数 | 3T（0 条空转） | **4T（1 条，默认）** | 6T（3 条） | 8T（5 条） | **18T（15 条）** |
|---|---|---|---|---|---|
| B 三分量并行（轮 1 / 轮 2） | 0.0348 / 0.0362 ms | **0.0335 / 0.0337** | 0.0334 / 0.0368 | 0.0345 / 0.0343 | **0.0427 / 0.0407（+27.5 % / +20.8 %）** |
| A master 整趟（单线程阶段） | 0.0769 / — | 0.0786 / 0.0789 | 0.0794 / — | 0.0792 / — | 0.0791 / 0.0883（+2.9 % / +11.9 %） |

  读法：**4T 比 3T 还略快（噪声级）⇒ 那一条空转线程的代价在噪声以下**；加到 8T 也才 +2～3 %；
  只有 18T 才明显（+21～28 %）。单线程阶段在高线程数下的残留税也只有几个百分点（两轮 +2.9 % / +11.9 %，
  波动量级）。生产管线的"全局回代"桶在同一轮会话内 4T→18T 是 505.0 → 643.9 ms（**+27.5 %**），
  与微基准逐字吻合 —— 因为两侧是**同一份工作**（都是 3 个分量），差别只是旁边多了 14 条自旋线程。
- **在 4T 下，限制 3 分量并行的已经不是自旋，而是内存系统**：3T 只拿到 2.12×、4T 2.28×（上限 3.00×），
  即 ~71–76 % 的并行效率 —— 三条独立链共享 L2/L3/DRAM 的结果。**减少自旋换不回这部分。**
- **还剩哪些"独占型"串行段**：只有两处 `omp single` —— 惯性右端（一次/子步，O(3N)）与判据合并
  （每迭代，几十个槽位的合并）。都很短 ⇒ 自旋窗口很窄。
- **没消掉的部分**：① 18T（我们刻意不用的档位）上 15 条空转对 3 条干活的干扰
  ≈ 139 ms / 300 子步 ≈ **0.46 ms/子步 ≈ 11 %**；② barrier 的"等最慢者 + 缓存行失效"
  （散射 7 次/迭代，单价 4T 4.02 µs → 18T 19.78 µs）—— 这一项与 Phase 4c 无关，仍在散射桶里。
- **结论**：**默认 4T 下这个问题已经低到测不出来**；它不再表现为"回代被拖慢"，
  只剩"最优线程数很小"这一条后果。要彻底消除仍需自建线程池 + 自适应等待（见 §3 的"不做"清单），
  但**期望收益现在集中在 18T 那个不使用的档位上** ⇒ 优先级低。

## 3. 明确"不做"的方向（附实测依据，别重复投入）

| 方向 | 为什么不做 |
|---|---|
| **层调度并行三角求解**（每层一次 barrier） | 层内工作量中位只有 288/492/948 项，与一次同步成本**同阶**；40×40 上光同步总量就超过串行回代本身（实测 0.81× 倒亏 42 %）；相对手写串行版只剩 1.18–1.36×（`solver-feasibility.md` §3） |
| **改变"等待发生的位置"**（把回代移出并行区域 = Phase 1 之前的结构） | 区域外线程池**仍在自旋**（实测紧跟 18 线程区域之后的串行段被拖慢近一倍：5.28 vs 10.29 ms）；老结构下回代同样被拖慢 1.39× ⇒ 换位置不改任何因子 |
| **`OMP_WAIT_POLICY=passive`** | 回代确实变快（−5.5 %…−16 %），但同步点太密（10 个/迭代 × 12,000 迭代），每次唤醒的代价把散射推到 +32 %…+708 % ⇒ 净亏（`perf.md` §6） |
| **换 OpenMP 运行时（libomp）** | 18T 下散射 323 → 3466 ms（`perf.md` §6.1） |
| **线程亲和性 / 固定"负责回代的线程"** | ❌ **已实测否掉**（2026-09-22，三组对照）：① 4 线程各占一个独立物理核（`start /affinity 5555`）2.992 vs 不绑 3.020（−0.9 %，噪声）；② 8 线程全绑到 8 个独立核 3.578 vs 不绑 3.123（**+14.6 %**）；③ 用诊断开关 `PD_AFFINITY`（`core/math/Parallel.{h,cpp}`，只在区域入口调一次）**只绑做回代的那 3 条线程、其余保持完全自由**：4T 3.317 vs 3.110（**+6.7 %**）、排他版（其余限 LP6..19）3.280（+5.5 %）；8T 同样更差（+2.1 % / +5.4 %）。<br>原因：8T 比 4T 差的那 6 % 主要来自**同步成本随线程数上升**（barrier 4T 4.02 → 8T 7.32 µs）与负载不均 —— **绑核解决不了**；而绑核会剥夺调度器自由度（慢线程不能被搬走），代价 2–15 %。<br>另注：所谓"工作线程独占 + 其他完全自由"在原理上不成立 —— **独占即排他**，要保证没人来抢就必须限制别人；本机 12 个物理核、18 线程的情形下更不可能。 |
| **残差改成"每条边只算一次"的按颜色版本** | 现在逐顶点 gather 的固有代价是每条边的投影被两个端点各算一次；改成按颜色边并行 + 逐顶点累加虽然只算一次，但**要额外加 C 个 barrier/迭代**（C=6）⇒ 得不偿失（Phase 3 的实测已经把 gather 版定下来了：4T −4.5…−11.3 %） |
| **弯曲 stencil 的"隔行采样"降本**（`PD_BEND_STRIDE >= 2`） | ❌ **已实测否掉（2026-09-22，`perf.md` §13.3）**：局部二阶差分约束只在**奇数**中心采样时，未被采样的中心顶点可以自由吸收全部曲率（把奇数顶点取成两侧偶数顶点的中点即精确满足全部被采样约束）⇒ **对粗尺度弯曲零阻抗**。实测：付 +11.5 % 代价，**k 加 100 倍应变只变 0.4 %**（对照完整采样 −75.5 %），截图与"关闭"逐像素级相同。反例已钉成断言 |
| **惯性右端并行化**（`omp single` → `omp for`） | ❌ **已实测否掉（2026-09-23，`perf.md` §14）**：这一步每子步只跑一次、是 O(n)=1600 顶点的纯读写（串行 3–5 µs），4T 下子步 2630 µs ⇒ **理论上限只有 0.1 % 量级**。三方 A/B（旧-single / 控制-single / 新-for）实测：1 线程档就已经"快" 1.7 %（单线程时两者等价 ⇒ 证明那是代码布局抖动而非并行），去掉这个地板后 4T/18T 只剩 −1.2 %/−0.6 %。**代码已回退**；方法论要点：凡"并行化/换写法"的对照，必须留一个**让该机制失效的档位**做对照 |

### 1.8 ✅ 线性（中点）弯曲约束（已完成 2026-09-22）；降代价的两个候选**已实测：一个可用、一个被否**

- **做了什么**：`Mesh::addBendingStencils` + `Assembler` 的弯曲块与常向量右端 + 残差两条口径
  （详见 `docs/perf.md` §12）。约束形式 $A_c x = x_a-2x_b+x_c$、$E=(k/2)\|A_cx\|^2$。
- **为什么选它**：`A_c` 常数 ⇒ 只分解一次；块是标量 × I₃ ⇒ 三分量并行保住；
  流形线性 ⇒ 投影恒 0 ⇒ 局部步与散射**一个字都不用改**。
- **量级与依据**（同轮交替 5 次取最小，40×40/iters40/300 子步/4T，`PD_BEND=1000`）：
  **单子步 2.57 → 4.45 ms（+73.4 %）**；L nnz 23,496 → 41,712（+77.6 %）；
  **因子 nnz 66,027 → 182,613（+176.6 %）**；全局回代 497 → 983 ms（+97.6 %，占总增量约 81 %）；
  投影+散射 +4.7 %（几乎没有！）；解包+判据 +39 %（残差多算一项力）。
- **是否改变数值**：⚠️ **是**（默认关闭 ⇒ 默认不变；开启后物理是另一套）。
- **默认**：`SceneConfig::bendStiffness = 0`（或 `PD_BEND=<k>` 覆盖）。开启后
  最终应变 max 0.0586 → 0.0499。
- **降代价的两个候选：已实测（2026-09-22，`docs/perf.md` §13；开关
  `PD_BEND_SAMPLING=standard|rows|cols|checker` / `PD_BEND_STRIDE=1|2|3`）**
  - ✅ **只加一个方向（rows/cols）：有效**。因子 nnz 182,613 → **94,077（−49 %）**、
    单子步 **+15.9 %**（对照全采样 +75.0 %）；但抗弯变成**各向异性** —— 这是**换材料**，
    不是"更便宜的同一材料"，刚度必须按各向异性重新标定。
  - ❌ **隔点加密（`stride >= 2`）：被否，而且是"退化"而不是"效果差一点"**。
    没被采样的中心顶点可以**自由吸收全部曲率**（把奇数顶点取成两侧偶数顶点的中点，
    被采样约束的 $A_c x$ **严格为 0**，而偶数子格子任意强弯）⇒ 付 +11.5 % 的代价、
    物理上几乎等于没开（**k 加 100 倍，应变只变 0.4 %**，对照完整采样 −75.5 %；
    截图与"关闭"逐像素级相同）。已钉成断言
    `stridedBendingSamplingCannotSeeCoarseBendingSoItIsRejected`；运行时会打警告但不改行为。
  - 推论（可复用的一般结论）：**"每个点上的局部二阶差分"这类约束不能靠抽样降本，
    只能靠"减维度"（少一个方向）降本。**
- **局限（不是待办，是设计取舍，见 `docs/perf.md` §12.6）**：
  等效抗弯刚度 $\propto s^4/k$ ⇒ **换网格要重标定**；边界是**自由端**（端点不生成 stencil）；
  静止曲率恒为 0 ⇒ **不能表达目标曲率/预折痕**（那需要二面角形式，规格在 `docs/plan.md` §2.2.5）。
