## 0. 当前基线（引用本文任何数字都以它为准）

主工况：40×40 / iters 40 / 300 子步 / `--residual-tol 0.3` / **4 线程**（默认）：

| 桶 | 累计 | 占比 | 备注 |
|---|---|---|---|
| **全局回代** | 500.8 ms | **57.0 %** | 已按 x/y/z 三分量并行；口径 = 阶段墙钟（含等最慢者） |
| 解包+判据 | 165.7 ms | 18.9 % | 含 1 个显式 barrier + 1 个判据 `single`；残差在这一桶 |
| 散射 | 102.8 ms | 11.7 % | 种子趟 + 6 个颜色轮 ⇒ **7 个 barrier / 迭代** |
| 局部步 | 87.4 ms | 10.0 % | 已并行；带宽受限 |
| 其它（预测/组装/速度/其它） | 21.5 ms | 2.4 % | 组装+分解是一次性（仅 stamp 变化时） |

- **单子步 2.91 ms**（300 子步 = 878 ms）；改造前同工况 18 线程 13.865 ms ⇒ 累计 **4.8×**；
  Phase 4b 之后是 5.02 ms，Phase 4c 又拿了 −41.8 %（同轮交替 5 次取最小）。
- **迭代单价降到 0.073 ms**（40 迭代/子步；Phase 4c 之前是 0.136 ms，`solver-feasibility.md` §6）。
- **线程数标定仍成立**：40×40 / 60×60 / 100×100 最优都是 **4T**；
  200×200 / iters10 上 4T (65.35 ms) 与 8T (64.74 ms) 在 **1 % 内平手** ⇒ 默认 4 不必改。
- **剩下的天花板**：把回代以外的一切并行到 0，也只能再拿 **−42 %**（505/878）；
  而回代本身在"精确三角求解 + 三分量"这个算法下的并行上限就是 **3 路**。

## 1. 优化机会（按预估收益排序）

### 1.1 减少迭代次数：40 → 20（**−49 %**，待拍板）

- **是什么**：把 `cfg.maxIterations` 从 40 降到 20（瞬态），或做外层加速让同样的精度用更少迭代。
- **为什么有效**：时间与迭代数**几乎严格成正比**（每迭代 = 一次"局部步→散射→回代→解包+判据"），
  而回代占 57 % ⇒ 少一半迭代就是近乎线性的一半时间。
- **量级与依据**：实测（Phase 4c 之前的二进制，40×40/300 子步）40 → 20 迭代 = **−49 %**，
  而最终弹性能只差 **0.5 %**（`solver-feasibility.md` §6）。而且瞬态本来就到不了判据：
  400 次迭代后残差仍停在 5.7 m/s²（判据 = 0.3·|g| = 2.943），每次只降 ~0.3 % ——
  所以瞬态的迭代数**本来就是硬截断**，不是"算到收敛"。
- **是否改变数值**：⚠️ **是**（弹性能 0.5 %、末次残差显著变化）。要按用途分档：
  交互预览 / 离线对照 / 回归基线可以取不同的预算。
- **怎么验**：`pd_bench --iters 10|20|40|80` 四档对照（命令见 `solver-feasibility.md` §8），
  看应变/能量/收敛统计三组物理量，再决定默认档。
- **备注**：若要求"同样精度但更快"，则要换方法（Chebyshev 外推 / APD / 多重网格），
  那是一次**方法改造**，要重新验收全部物理正确性（`docs/pd-convergence.md` §5.2 有候选清单）。

### 1.2 投影与散射融合（3–8 %，**逐位不变**）

- **是什么**：现在每迭代是"先 `projectInRegion` 把每条边的投影 d_c 写进 `targets`（物化），
  再 `scatterIntoInRegion` 读 `targets` 累加到 b"。融合即：**按颜色就地算 d_c 并直接累加到两端点**，
  不再物化 `targets`，且颜色 0 直接以 `bBase` 为基数写（省掉整趟"种子趟 `b = bBase`"）。
- **为什么有效**（机制，按当前单迭代 73 µs 折算）：
  ① 省掉 `targets` 的一次写 + 一次读：40×40 是 3120 边 × 24 B ≈ **75 KB / 迭代**（写+读 = 150 KB）；
  ② 每条边的两个端点位置现在被读两遍（投影一趟、散射一趟），融合后**只读一遍**（再省 ~150 KB）；
  ③ 省掉种子趟：O(dim)=4800 double ≈ 38 KB 写 + **1 个 barrier / 迭代**。
  这三笔都是"纯冗余"，不影响任何算术。
- **量级与依据**：把上面 300 KB/迭代按 4 线程的有效带宽折算，粗估 **3–8 %**
  —— **这是估算，未实测**，所以第一步应该是微基准/分支 A/B，而不是直接落地。
- **是否改变数值**：✅ **不改变**。每个顶点被累加的颜色顺序（0…C−1）与现在完全一致，
  投影的输入（当前 `positions`）也一致 ⇒ 结果应当**逐位相同**（可用现成的逐字比对验收）。
- **怎么验**：分支实现 → 同轮交替 A/B（4T/18T、40×40 与 100×100）→ 逐字比对物理输出。
- **风险**：本仓库有过教训（`docs/perf.md` §7.3）：**热路径里加一点点东西也可能很贵**
  （在散射里加一个 O(1) 契约校验让 1T 散射 +28 %，是编译器代码布局被扰动）。
  融合会改变散射内层循环的形态，必须实测而不是推理。
- **备注**：这正是 `docs/plan.md` §3 写的"改造后目标形态"，一直没实施（当时为了保守起见保留了物化）。

### 1.3 因子只存一份（未测，主要对大规模有意义）

- **是什么**：`L = Ã ⊗ I₃` ⇒ 因子的三个分量块**结构同构、数值完全相同**（实测每分量 nnz 相等：
  40×40 各 22,009；100×100 各 212,411；200×200 各 1,085,011）。现在它们在同一个 CSC 因子矩阵里
  **各存了一份**。理论上可以只存一份标量因子 + 分量映射，三条线程用同一份因子配不同右端。
- **为什么有效**：内存足迹降到 1/3（200×200：39 MB → **13 MB**，按每非零 12 B 估）。
  这台的 P-core L2 是 1.25 MB、L3 是 25 MB：
  · 40×40 的因子 0.79 MB 本来就住得进 L2 ⇒ 收益很小；
  · 200×200 的 39 MB 远大于 L3，缩小到 13 MB 也仍大于 L3 ⇒ **收益不确定**，得实测。
  另外三条线程读同一份数据时，L3 里是同一份副本（现在读的是三块不同地址）⇒ 对 L3 命中率有利。
- **是否改变数值**：✅ 不改变（同一份数据、同样的列顺序）。
- **怎么验**：可以在 `pd_solvecomp` 里先量"三分量并行读同一份因子"vs"读各自那份"的单次 solve 时间，
  再决定动不动生产代码。

### 1.4 减少同步点密度（收益在散射桶里，但要**重做位级基线**）

- **是什么**：散射每迭代有 `1 + C` 个 barrier（种子趟 + C 个颜色轮，40×40 实测 C = 6）。
  减少颜色数、或把种子趟并进第一色（见 1.2），都能减少同步点数量。
- **为什么有效**：`B(P)`（每次同步的成本）在负载中实测约 **1.1 µs × 线程数**
  （4T 4.02 µs / 8T 7.32 / 18T 19.78，空载只有 0.08 µs×P —— 空载会低估 12 倍），
  且每次同步都要"等最慢者 + 18 份缓存副本失效"。同步点从 10 个/迭代降到 8 个就是 20 % 的同步开销。
- **量级与依据**：`docs/perf.md` §5 的归因表里，"散射的颜色轮 barrier + 残余写争抢"在 18T 上
  贡献了 +509 ms（占 18T−1T 差额的 46 %）。4T 下这一项小得多，预计**几个百分点**。
- **是否改变数值**：⚠️ **是**。颜色数是"顶点上各条边的求和顺序"的来源，改它会让**位级结果变化**
  （仍然是确定性的、仍与线程数无关，但不再与旧基线逐字相同）⇒ 必须重新记录物理基线，
  失去"逐位不变"这张免验收通行证。这是它比 1.2 贵得多的地方。
- **怎么验**：改 `ConstraintColoring` 的着色策略（例如合并层/贪心更少色），
  用 `test_primitives` 的着色断言 + 全部物理基线重采。

### 1.5 分块流水：把回代从 3 路推到 4 路以上（改变数值，性价比低）

- **是什么**：把每个分量的因子切成两块 `[[L11,0],[L21,L22]]`，解 x1 = L11⁻¹b1（串行）→
  用 x1 更新 b2' = b2 − L21·x1（**这一步是稀疏矩阵乘向量，可按行并行**）→ 解 x2 = L22⁻¹b2'。
- **为什么"可能"有效**：现在 4 线程里只有 3 条在干活（3 个分量），第 4 条空转；分块后更新段变成 6 路可并行。
- **为什么**性价比低：三段之间有先后依赖，只有中间那段能多拿并行度（平均 ≈3.5–4 路），
  还要再加上同步；而**求和顺序会变**（更新项与块内的项不再按"对方列号递增"逐个相减）
  ⇒ 不再逐位不变 ⇒ 要重做物理基线。收益小 + 代价大 ⇒ 排在最后。

### 1.6 换全局步形态（量级大，但都是大工程）

- **1.6.1 迭代法替代直接解**（Chebyshev 半迭代 / CG / 多重网格 / 近似逆）：把"延迟受限的串行链"
  换成"带宽受限的 SpMV 序列"，天然高并行。代价：全局步变成**不精确求解**，外层 PD 迭代数与收敛
  行为会变（要重新验收）；而且门槛被 Phase 4c 抬高了 —— 直接法已经快了 2.0–2.8×。
- **1.6.2 超节点 + 嵌套剖分(ND) + 依赖计数 + 工作窃取**（CHOLMOD/SuperLU_DIST 形态）：
  真正的可扩展并行三角求解形态（同步次数 O(深度) 而不是 O(层数)）。需要：换排序（现在 AMD 的关键路径
  310/1042/2250 层）、稠密块核、自建线程池（MSVC 经典 OpenMP 连 `task` 都没有），且自建同步在 18T 上
  实测会**活锁**（必须带 yield 回退）。
- **1.6.3 GPU Chebyshev（M6）**：唯一能从根上"消除"串行段的路线（见 `docs/plan.md` M6 与 D13）。
- **是否改变数值**：⚠️ 三者全部要重新验收物理正确性。

### 1.7 数字收尾（不改代码，只是把话说准）

- **200×200 长日志**：A/B 与看板里 200×200 只用 8–12 子步，一次性"组装+分解"被摊进单子步
  ⇒ 报出的 −28.6 % 是**偏保守**的。要准数字就跑 100+ 子步（同轮交替 5 次约 1 分钟）。
- **查看器重测**：60×60 稳态"物理 0.90 ms/帧"是 Phase 4c **之前**的数字，本轮未重测
  （查看器自报数字波动大，只适合定性；要跑 `pd_viewer --frames 400`）。

## 2. 现存问题（按严重度排序）

### 2.1 ⚠️⚠️ **IPC 会破坏 `⊗ I₃` 结构（战略问题，最要紧）**

- **是什么**：Phase 4c 的全部收益建立在 `L` 的每一块都是**标量 × I₃** 之上。
  项目最终目标包含 **IPC**（增量势接触），而 IPC 的 barrier / friction Hessian 是
  **一般的（非各向同性）3×3 块**。
- **为什么会出问题**：非各向同性的块会让消元填充**跨越"分量"**（现在三个分量是三个互不相连的连通分量），
  `EigenDirectSolver::buildComponents()` 的检查会命不中 ⇒ `parallelComponents()` 返回 1 ⇒
  **功能仍然正确，但那 2.0–2.8× 的加速静默消失**，回到 Phase 4b 的水平（多出 ~40 % 时间）。
- **量级与依据**：`pd_solvecomp` 的第一节会直接打印"跨分量的 i≠j 项"，现在三档规模都是 **0**；
  引入接触项后这个数会 > 0。
- **怎么修/怎么办**（三选一，需要拍板）：
  ① **接受**：CPU 直接法路线在接触场景下退回 Phase 4b 的速度；
  ② **为接触项设计保持结构的形式**（例如接触力只用对角近似、或把接触块放在单独的子系统里）；
  ③ **不再指望这条**：把大网格的并行寄望于 1.6.2 / 1.6.3。
- **配套动作**（无论选哪条都要做）：把 `pd_solvecomp` 纳入验收集当门禁或给它加断言，
  否则这件事会以"某天突然慢了 2 倍但没人知道"的形式出现（见 2.2）。

### 2.2 结构回退是**静默**的

- **是什么**：`IGlobalSolver::parallelComponents()` 在结构不满足时返回 1，`Integrator` 就退回整趟求解。
  这个设计是**故意的**（保证新矩阵形态不会算错，只会变慢），但它**不打印任何提示**。
- **影响**：配合 2.1，将来加速丢失时没有任何信号；性能回归会被归因成"机器变了"。
- **建议**：回退时打印一次告警（`std::fprintf(stderr, ...)` + 一个 `static bool` 只打一次），
  并在 `pd_bench` 的输出里明写"本次运行的全局步是 X 路并行"。

### 2.3 `solveComponent` 的统计竞争（**本轮改造引入的**）

- **是什么**：`EigenDirectSolver::solveComponent()` 里，三条线程会并发执行
  `stats_.lastSolveSeconds = ...` 与 `stats_.totalSolveSeconds += ...`（非原子读-改-写）。
  `solveCalls` 只在 `c == 0` 时自增，是单写者，**无竞争**。
- **为什么是问题**：形式上这是**数据竞争**（C++ 层面 UB）；实际影响极小 ——
  每线程 12,000 次累加、每次窗口几纳秒、单次调用间隔约 200 µs ⇒ 单次碰撞概率 ~1e-5
  ⇒ 整轮期望丢更新 < 1 次 ⇒ 读数误差 < 0.1 %。但本仓库对"确定性"是有承诺的，
  诊断数字也不该有 UB。
- **怎么修**（两个方案，二选一）：
  ① 让统计**不再由分量线程写**：给 `IGlobalSolver` 加 `noteSolveStage(double)`，
     由 `Integrator` 在 `omp for` 结束（barrier 之后）**单线程调用一次**；
     `totalSolveSeconds` 的语义随之从"各分量耗时之和"变成"阶段墙钟"（更干净，且与新桶口径一致）。
  ② `Impl` 里改成 per-component 槽位（每个槽只有自己的线程写），暴露时再汇总 ——
     但 `stats()` 返回的是 `const Stats&`，汇总需要额外的时机，比 ① 绕。
- **注意**：修完要同步 `app/bench/main.cpp` 的"单次回代"那一行（现在用 `累计/次数`）与
  `_verify/scale_sweep.cpp` 的"回代总 ms"一列，它们的口径要跟着说清。

### 2.4 "全局回代"桶的口径变了，历史数字不可直接比较

- **是什么**：Phase 4c 之前该桶是 `omp single` 里"唯一执行者自己的执行时间"（**不含** barrier 等待）；
  现在是按分量 `omp for` 之后的**阶段墙钟**（**含**等最慢的那条线程）。
- **影响**：引用历史上"回代占 76 %"之类的数字时会得出错误结论。
- **现状**：已在 `docs/perf.md` §9.6、`build/_perf/HANDOFF.md` 坑 12、看板第六章注明。
  引用时必须写明口径。

### 2.5 `solveComponent` 的不 resize 契约

- **是什么**：拆分路径**刻意不 resize** 输出向量 x（多线程并发 resize 是竞争），
  要求调用方在进并行区域之前把 `xSolution` 备成长度 n，否则 `abort`。
- **影响**：将来若有别的调用方（GPU 后端、批处理、新的诊断工具）不知道这条契约，会直接崩。
- **现状**：已在 `IGlobalSolver.h` 的契约里写明；`Integrator` 靠 `ensureBuffers()` 保证。

### 2.6 M2 判据口径未按"带宽效率"改写

- **是什么**：`docs/plan.md` M2 写的是"8 线程局部步 ≥ 5×（N ≥ 40k）"，200×200 实测只有 **2.36×**。
- **为什么达不到**：这不是实现问题 —— 局部步每次读写约 8.3 MB，1 线程已达 ~17 GB/s，
  8 线程 ~40 GB/s ≈ 该平台双通道峰值的 **78 %**，要 5× 需要 ~85 GB/s（超过平台能力）。
- **建议**：把判据改成带宽效率口径（例如"≥70 % 平台峰值带宽"），但这**需要拍板**。

### 2.7 `_verify/` 下约 20 个诊断程序前提过期

- **是什么**：排查期留下的诊断程序（`docs/code-map.md` §2.7），多数假设已经过期，
  **不是受支持的验收集**。
- **风险**：后人拿它当基准会得到错误结论。
- **建议**：清理或逐个加"过期/仅诊断"标注。

### 2.8 测量成本：跨会话数字不可比

- **是什么**：同一二进制同工况在会话内会漂移（实测 200×200 从 155 ms 一路降到 123 ms）。
- **影响**：任何改动都必须在**同一轮会话内交替 A/B、重复取最小值**；跨会话对比无效。
- **现状**：这是纪律不是缺陷（`docs/perf.md` §0/§6.2），但它是每条优化都要付的成本。

### 2.9 自旋抢资源（Phase 4c 之后：默认档已测不出来，高线程数下仍在）

- **是什么**：等待仍然由 vcomp 的**自旋**实现（`OMP_WAIT_POLICY` 默认 active）—— 这是 runtime 行为，
  Phase 4c 没有改它，改的是"谁在等、等多久、几条线程在等"。
- **形态变了**：Phase 4c 之前，全局回代是 `omp single` ⇒ "1 条线程干活、P−1 条在 barrier 上自旋"，
  而这个阶段占单子步 57–76 %、4T 下自旋:工作 = **3:1**、18T 下 = **17:1**。
  现在按三分量 `omp for` ⇒ "3 条干活、P−3 条自旋"（4T = 1:3、18T = 5:1），
  且回代阶段本身短了 2.0–2.8× ⇒ **自旋窗口同比缩短**。
- **自旋 CPU 的绝对量**（40×40 / iters40 / 300 子步，按回代桶折算的"空转 CPU 时间"）：
  4T 从 ~280 µs/迭代降到 **~42 µs/迭代（6.7×）**；18T 从 ~2108 µs 降到 **~805 µs（2.6×）**。
- **剩余量级**（`pd_solvecomp` 两轮独立测量，单次 solve 的最小值；A 档是单线程阶段、B 档是三分量并行）：

| 线程数 | 3T（0 条空转） | **4T（1 条，默认）** | 6T（3 条） | 8T（5 条） | **18T（15 条）** |
|---|---|---|---|---|---|
| B 三分量并行（轮 1 / 轮 2） | 0.0348 / 0.0362 ms | **0.0335 / 0.0337** | 0.0334 / 0.0368 | 0.0345 / 0.0343 | **0.0427 / 0.0407（+27.5 % / +20.8 %）** |
| A master 整趟（单线程阶段） | 0.0769 / — | 0.0786 / 0.0789 | 0.0794 / — | 0.0792 / — | 0.0791 / 0.0883（+2.9 % / +11.9 %） |

  读法：**4T 比 3T 还略快（噪声级）⇒ 那一条空转线程的代价在噪声以下**；加到 8T 也才 +2～3 %；
  只有 18T 才明显（+21～28 %）。单线程阶段在高线程数下的残留税也只有几个百分点（两轮 +2.9 % / +11.9 %，
  波动量级）。生产管线的"全局回代"桶在同一轮会话内 4T→18T 是 505.0 → 643.9 ms（**+27.5 %**），
  与微基准逐字吻合 —— 因为两侧是**同一份工作**（都是 3 个分量），差别只是旁边多了 14 条自旋线程。
- **在 4T 下，限制 3 分量并行的已经不是自旋，而是内存系统**：3T 只拿到 2.12×、4T 2.28×（上限 3.00×），
  即 ~71–76 % 的并行效率 —— 三条独立链共享 L2/L3/DRAM 的结果。**减少自旋换不回这部分。**
- **还剩哪些"独占型"串行段**：只有两处 `omp single` —— 惯性右端（一次/子步，O(3N)）与判据合并
  （每迭代，几十个槽位的合并）。都很短 ⇒ 自旋窗口很窄。
- **没消掉的部分**：① 18T（我们刻意不用的档位）上 15 条空转对 3 条干活的干扰
  ≈ 139 ms / 300 子步 ≈ **0.46 ms/子步 ≈ 11 %**；② barrier 的"等最慢者 + 缓存行失效"
  （散射 7 次/迭代，单价 4T 4.02 µs → 18T 19.78 µs）—— 这一项与 Phase 4c 无关，仍在散射桶里。
- **结论**：**默认 4T 下这个问题已经低到测不出来**；它不再表现为"回代被拖慢"，
  只剩"最优线程数很小"这一条后果。要彻底消除仍需自建线程池 + 自适应等待（见 §3 的"不做"清单），
  但**期望收益现在集中在 18T 那个不使用的档位上** ⇒ 优先级低。

## 3. 明确"不做"的方向（附实测依据，别重复投入）

| 方向 | 为什么不做 |
|---|---|
| **层调度并行三角求解**（每层一次 barrier） | 层内工作量中位只有 288/492/948 项，与一次同步成本**同阶**；40×40 上光同步总量就超过串行回代本身（实测 0.81× 倒亏 42 %）；相对手写串行版只剩 1.18–1.36×（`solver-feasibility.md` §3） |
| **改变"等待发生的位置"**（把回代移出并行区域 = Phase 1 之前的结构） | 区域外线程池**仍在自旋**（实测紧跟 18 线程区域之后的串行段被拖慢近一倍：5.28 vs 10.29 ms）；老结构下回代同样被拖慢 1.39× ⇒ 换位置不改任何因子 |
| **`OMP_WAIT_POLICY=passive`** | 回代确实变快（−5.5 %…−16 %），但同步点太密（10 个/迭代 × 12,000 迭代），每次唤醒的代价把散射推到 +32 %…+708 % ⇒ 净亏（`perf.md` §6） |
| **换 OpenMP 运行时（libomp）** | 18T 下散射 323 → 3466 ms（`perf.md` §6.1） |
| **线程亲和性 / 固定干活线程** | 默认 4T 下回代惩罚本来只有 1.06×，SMT 冲突在 8 线程时已基本不存在 ⇒ 性能期望 ≈0；降级为**机制探针**（回答"干扰主要来自 SMT 还是缓存/频率"） |
| **残差改成"每条边只算一次"的按颜色版本** | 现在逐顶点 gather 的固有代价是每条边的投影被两个端点各算一次；改成按颜色边并行 + 逐顶点累加虽然只算一次，但**要额外加 C 个 barrier/迭代**（C=6）⇒ 得不偿失（Phase 3 的实测已经把 gather 版定下来了：4T −4.5…−11.3 %） |

## 4. 建议顺序（按"收益 ÷ 代价"）

1. **修 2.3**（统计竞争）—— 约 15 行、3 个文件，消除一个自己引入的 UB。
2. **验 1.2**（投影与散射融合）—— 唯一"逐位不变 + 几个百分点"的候选，且本来就是计划里的目标形态；
   先做分支 A/B，不要直接落地。
3. **收口 2.1/2.2**（IPC 结构风险）—— 至少先把 `pd_solvecomp` 纳入验收集 + 回退告警，
   否则将来会静默丢加速。
4. **1.7 数字收尾**（200×200 长日志、查看器重测）。
5. **拍板 1.1**（迭代预算）—— 量级最大（−49 %），但那是精度取舍，必须由项目定档。
6. 大工程（1.5 / 1.6）留到"CPU 直接法这条路被明确选定/放弃"之后再排。
